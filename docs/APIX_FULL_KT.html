System Overview

High-level architecture, component map, and multi-chain support.

What is APIX?

APIX (Initial API Offering) is a decentralized API marketplace that enables developers to monetize their APIs through a bonding curve token model. Users pay per API call, earn tokens proportional to usage, and once enough tokens are distributed (graduation), liquidity auto-deploys to a DEX.


The core innovation is the pay-after-success model: users are only charged if the API returns a successful response. Token distribution is tracked virtually in Firestore and committed on-chain at graduation via a Merkle tree airdrop.

Payment Protocol (x402 v2)

EVM (Base Sepolia)

Uses EIP-3009 TransferWithAuthorization signed to the facilitator address (not the token address). The Thirdweb facilitator handles on-chain settlement and forwards payment to the token contract.

Solana (Devnet)

Uses a pre-signed SPL token transfer transaction. The backend deserializes and submits the transaction on-chain after builder success.

Protocol Flow

  1. Client makes initial API request (no payment header)
  2. Backend returns 402 Payment Required with fee details
  3. Client signs payment authorization (EIP-712 for EVM, SPL transfer for Solana)
  4. Client retries request with PAYMENT-SIGNATURE header (base64 JSON)

Key Hook: useX402Payment

Most Important Frontend Hook

Handles the complete payment + API call flow. This is the primary interface between the user's wallet and the backend proxy.

  1. Make initial API request (no payment header)
  2. Receive 402 Payment Required response with fee details and facilitator address
  3. Sign payment authorization:
    -- EVM: EIP-712 TransferWithAuthorization to facilitator
    -- Solana: SPL token transfer instruction (signed)
  4. Retry request with PAYMENT-SIGNATURE header (base64 JSON)
  5. Return API response data to the calling component

EVM Signing Details

// EIP-712 TransferWithAuthorization message
{
  from:        userAddress,           // payer wallet
  to:          facilitatorAddress,    // Thirdweb facilitator (NOT token address)
  value:       feeAmount,             // USDC amount in smallest unit
  validAfter:  now - 60s,             // grace window
  validBefore: now + 3600s,           // 1-hour expiry
  nonce:       randomBytes32          // unique per authorization
}

// Domain: USDC on Base Sepolia

Race Condition Protection

3 Layers of Protection Against Concurrent Graduation

Layer 1: Cloud Tasks named task deduplication -- Duplicate dispatch returns gRPC ALREADY_EXISTS; the second dispatch is silently rejected.

Layer 2: Firestore atomic transaction -- incrementVirtualDistributedWithEarnings() uses a Firestore transaction that caps virtualDistributed at the graduation threshold. Even concurrent calls cannot exceed it.

Layer 3: Graduation lock -- A Firestore document with a 5-minute TTL prevents concurrent execution of the graduation handler. If the lock exists and is not expired, subsequent calls are rejected.

5.2 IAOTokenFactory — How Tokens Are Created

The factory uses Clones.cloneDeterministic() to deploy minimal proxy contracts at deterministic addresses. The salt is derived from the server slug: 

salt = keccak256(abi.encodePacked(serverSlug))

Each clone is initialized with:

  • name and symbol — token identity
  • slug — server slug for lookup
  • builder — the API developer's address
  • paymentToken — USDC address
  • graduationThreshold — 62.5% of 1B tokens

1 billion tokens are minted to the TokenDistributor contract on creation. The factory emits:

event TokenCreated(string serverSlug, address builder, address token);

PaymentTokenInfo Struct

struct PaymentTokenInfo {
    uint256 price;                    // Tokens per payment token (e.g., 25000 per USDC)
    address paymentToken;
    uint256 paymentTokenDecimals;     // 6 for USDC
    uint256 graduationThreshold;      // Basis points (6250 = 62.5%)
    uint160 sqrtPriceX96Token0;       // Initial sqrt price (token is token0)
    uint160 sqrtPriceX96Token1;       // Initial sqrt price (token is token1)
}

5.5 Liquidity Deployment at Graduation

When totalTokensDistributed >= graduationThreshold, the following sequence executes:

  1. Deploy LpGuardHook (whitelists IAOToken as pool initializer)
  2. Initialize Uniswap V4 pool: fee 10000 (1%), tick spacing 200
  3. Mint full-range LP position: 375M remaining tokens + 60% of collected fees (USDC)
  4. LP NFT owned by IAOToken contract (protocol-owned liquidity)
  5. LpGuardHook prevents unauthorized pool re-initialization

6.4 Merkle Claim Verification

Leaf hash construction (matches backend generation):

// Leaf data: 32-byte pubkey || 8-byte little-endian amount
leaf_data = pubkey_32bytes || amount_u64_le

// Double-hash for second preimage resistance
inner_hash = keccak256(leaf_data)
leaf = keccak256(inner_hash)

Proof verification walks sorted pair hashes upward to the root.

6.8 Gotchas

Solana-Specific Pitfalls:
  • 4KB BPF stack limit: Split instructions with many init accounts into separate instructions (can be in the same transaction).
  • Case sensitivity: Solana addresses are base58 and CASE SENSITIVE. Never call .toLowerCase() on them.
  • Version mismatch: Anchor 0.29 + CLI 0.32.1 version mismatch warnings are benign and can be ignored.
  • Keccak vs SHA-3: keccak::hash produces original Keccak-256 (same as Ethereum's keccak256), NOT the NIST SHA-3 standard.

7. Token Lifecycle & Bonding Curve

7.1 Lifecycle Overview

7.2 Phase 1: Token Creation

Two-step registration process:

  1. Validate: Frontend sends POST /api/register without tokenAddress. Backend checks slug uniqueness, API URL reachability (must return 200), and no duplicate endpoints.
  2. On-chain: Frontend creates the token via Factory.createToken() (EVM) or create_token + initialize_token_vault instructions (Solana).
  3. Register: Frontend sends POST /api/register again with tokenAddress. Backend stores token metadata in Firestore.

7.3 Phase 2: Bonding Curve

Formula:

tokensEarned = (fee x paymentTokenPrice) / 10^paymentTokenDecimals

Example calculation:

Fee10000 (0.01 USDC, 6 decimals)
Price25,000,000,000,000,000,000,000 (25k tokens per USDC)
Decimals6
Result250 tokens (18 decimals on EVM)

Atomic Update: incrementVirtualDistributedWithEarnings()

A single Firestore transaction updates BOTH the token document AND the earnings document:

  • Caps at graduation threshold (no overflow past 62.5%)
  • Tracks: virtualTokensDistributed, totalFeesCollected, pendingFeesForDistribution

7.4 Graduation Thresholds

Chain Threshold Raw Value
EVM 625M tokens 625000000000000000000000000 (18 decimals)
Solana 625M tokens 625000000000000000 (9 decimals)

Override for testing: set TEST_GRADUATION_THRESHOLD environment variable.

7.5 Phase 3: Graduation

When virtualTokensDistributed >= threshold:

  1. Dispatch Cloud Task (dedup via named task to prevent duplicates)
  2. Acquire graduation lock (5-minute TTL in Firestore)
  3. Build Merkle tree from all token-earnings entries
  4. Compute leaf hashes:
    • EVM: ABI.encode(['address', 'uint256'], [user, amount]) — OpenZeppelin-compatible
    • Solana: keccak256(keccak256(pubkey_32bytes || amount_u64_le)) — double-hashed
  5. Store tree in Firestore merkle-trees collection
  6. Invoke Cloud Function for on-chain graduation
  7. Cloud Function: set Merkle root + deploy liquidity atomically

7.6 Phase 4: Claiming

  1. GET /api/claim/:serverSlug/:userAddress — returns Merkle proof and amount
  2. User calls contract: claim(amount, proof[]) on EVM, merkle_claim on Solana
  3. Backend marks claimed = true in token-earnings

7.7 Phase 5: Trading

Post-graduation, tokens trade on decentralized exchanges:

  • EVM: Uniswap V4 (protocol-owned liquidity, LP NFT held by contract)
  • Solana: Raydium CLMM (placeholder for future implementation)

8. Fee Distribution System

8.1 Fee Accumulation

Every successful API call adds to two counters on the token document:

  • totalFeesCollected — cumulative USDC earned (never decremented)
  • pendingFeesForDistribution — USDC not yet distributed (reset after distribution)

8.2 Weekly Distribution Flow

  1. Cloud Scheduler triggers every Sunday at midnight UTC
  2. Backend fetches all non-graduated tokens with pendingFeesForDistribution > 0
  3. Groups tokens by chainId
  4. Calls the appropriate Cloud Function (EVM or Solana)
  5. Cloud Function executes on-chain fee distribution
  6. Callback to backend clears pendingFeesForDistribution

8.3 Fee Split

Post-Graduation 70% 10% 20% (token buyback)

11.2 Key Data Types

BigInt Storage: All BigInt values (token amounts, thresholds, fees) are stored as strings in Firestore to prevent JavaScript precision loss beyond Number.MAX_SAFE_INTEGER.
Address Normalization:
  • EVM: All addresses are lowercased before storage and lookup.
  • Solana: Addresses are stored as-is (base58, case sensitive). Never lowercase them.
The backend's normalizeAddress() utility handles this automatically based on chain type.
